# 服务器环境与远程推理报告

更新时间：2026-08-30

## 结论

远程推理链路已经实际跑通：

```text
本机 IsaacLab（RTX 3060）
  state + front + wrist
          |
          | gRPC over SSH tunnel
          v
服务器 LeRobot PolicyServer（RTX 4090）
          |
          | 60-action chunk
          v
本机 action queue -> 30 Hz 策略动作 -> 60 Hz IsaacLab env.step
```

最终 600 个物理步 GUI 双相机测试结果：

| 指标 | 结果 |
| --- | ---: |
| IsaacLab wall loop | 59.2 Hz |
| action chunk | 15 |
| observation 上传 | 15 |
| action queue underflow | 0 |
| 观测上传平均延迟 | 449.6 ms |
| 观测上传范围 | 308.0-551.6 ms |
| chunk 端到端平均延迟 | 476.2 ms |
| chunk 端到端范围 | 338.7-571.9 ms |
| 服务器 ACT 推理平均耗时 | 12.0 ms |
| 服务器完整 chunk 生成平均耗时 | 20.8 ms |
| 小消息 gRPC RTT 中位数 | 36.1 ms |

远程方案满足当前仿真验证需求。主要瓶颈是两路未压缩 `640x480 RGB` 图像上传，
不是服务器 GPU 推理。

## 最新功能验收

2026-08-30 使用当前服务器端口完成两轮 GUI 双相机验证：

- 本地客户端自动启动 SSH 隧道，输入一次密码后连接服务器 PolicyServer。
- B 后收到 60-action chunk，并连续执行 360 个物理步；9 个 chunk，queue underflow 为 0。
- R 在首个 chunk 仍在网络传输时重置，旧 chunk 没有进入新 episode。
- 再次 B 可重新开始；N 在执行 112 个物理步后停止并重置，随后保持等待 B。
- 正常结束和 Ctrl+C 后本地 18080 端口均被释放，无残留 `ssh -N` 进程。

本轮桌面 GUI 的 wall loop 约 40-45 Hz，网络上传约 0.3-0.9 秒。该数值受当前桌面窗口
尺寸和同时运行程序影响，不改变异步队列验收结论；30 Hz 策略队列没有欠载。

## 正式使用

### 1. 启动服务器 Policy Server

```bash
cd /home/a/lwh_code/lwh_robot_learning
python3 scripts/start_remote_policy_server.py
```

启动器读取 `configs/remote_policy_server_config.py`，自动登录服务器并执行远端服务脚本。看到
`[策略服务端] 已启动` 后保持终端运行。

### 2. 本机启动 Isaac Sim 客户端

当前服务器连接信息保存在本机 `configs/remote_policy_server_config.py`。该文件包含密码，权限
为 `600` 且不会提交到 Git。云平台实例变化时修改该文件中的 `host`、`port` 和
`password`。

打开第二个终端。客户端读取配置，自动认证、创建 SSH 隧道，并在退出时回收：

```bash
conda activate isaac
cd /home/a/lwh_code/lwh_robot_learning

python3 scripts/run_policy_client.py
```

等待 `[策略客户端] 已就绪，等待按 B 开始`。按 B 开始；R/N 停止当前策略并重置；
重置后再次按 B。客户端不会连接真实 follower。

服务器只监听 `127.0.0.1:8080`，不会向公网直接开放 pickle/gRPC 接口。云平台重建
实例后只需修改配置文件中的 `host`、`port` 和 `password`，两个启动命令都不用改变。

## 参数解释

| 参数 | 当前值 | 含义 |
| --- | ---: | --- |
| `policy_hz` | 30 | 每秒消费 30 个策略动作，与数据集 FPS 一致 |
| `actions_per_chunk` | 60 | 每次返回约 2 秒动作，足以覆盖公网延迟 |
| `chunk_size_threshold` | 0.65 | 剩余约 39 个动作（1.3 秒）时预取下一段 |
| `render_interval` | 2 | 60 Hz 物理下每两步更新一次相机，即约 30 Hz |
| `camera_mode` | dual | 只发送 front+wrist，不发送 overview |
| `timeout_s` | 5 | chunk 请求超过 5 秒后允许重试 |

客户端启动后等待 B；按 B 后先等待首个 chunk，不会在空队列状态下执行。运行中观测
在独立线程上传，并且同一时间只允许一条观测在途，因此公网传输不会阻塞 60 Hz 仿真
循环。R/N reset 会丢弃网络中尚未返回的旧 chunk，避免旧轨迹作用于新场景。

## 性能分析

两路 RGB 数组每次约为：

```text
2 x 640 x 480 x 3 bytes = 1,843,200 bytes
```

最终测试约每 0.7 秒发送一次观测，持续上行数据约 2.7 MB/s（不含协议和 SSH 开销）。
服务器 4090 生成 60 个动作只需约 20.8 ms，端到端平均 476.2 ms 中约 450 ms 都花在
图像序列化和公网上传。因此不要改回逐帧同步推理。

ICMP ping 被服务器屏蔽，因此网络基线使用 SSH 隧道内的 gRPC 小消息测量：20 次平均
51.9 ms，中位数 36.1 ms，范围 26.9-168.1 ms。
