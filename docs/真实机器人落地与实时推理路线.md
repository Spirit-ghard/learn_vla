# 真实机器人落地与实时推理路线

本文用于区分当前仿真验证方案和真实机器人可用方案，并记录后续 FlashRT 加速计划。

FlashRT 官方仓库：[https://github.com/flashrt-project/FlashRT](https://github.com/flashrt-project/FlashRT)

## 先明确当前方案的边界

当前项目已经完成的是：

```text
本机 Isaac Sim
  -> 双相机和关节状态
  -> SSH 隧道
  -> 服务器 LeRobot Policy Server
  -> 异步 action chunk
  -> 本机仿真执行
```

这适合验证 observation/action schema、模型行为、队列策略和网络延迟，但不能直接视为真实
机器人安全架构。真实机器人不能因为远程服务暂时没有返回，就把最后一个动作无限保持下去；
必须有本机 watchdog、动作限幅、速度/加速度限制、碰撞保护和急停。

## 真实落地的分层结构

### 1. 设备与低级控制层

- 电机、驱动器和机器人控制器负责位置/速度/力矩闭环。
- 控制周期通常高于策略周期，不能由 VLA 直接替代。
- 急停、限位、过流、碰撞和通信超时应在本机或控制器侧生效。

### 2. 传感器层

- 相机采集线程固定 FPS，使用有界帧队列，旧帧应丢弃而不是无限积压。
- 每帧必须带采集时间戳；state 和 image 要检查时间差。
- 预处理应尽量固定尺寸、颜色格式、归一化方式和内存布局。
- 不能只看相机 FPS，还要看“最新有效帧到策略输入”的实际延迟。

### 3. 策略层

- VLA 通常低频输出动作，使用 action chunk、插值或保持策略连接到更高频的控制器。
- 策略推理线程不能阻塞安全线程和低级控制线程。
- 队列耗尽时进入明确的安全状态，例如减速停止或回到安全姿态，而不是无限保持旧动作。
- 模型异常、NaN、动作越界、图像失效和时间戳过期都应被拦截。

### 4. 资源与运维层

- 为 GPU 显存、CPU 核、相机带宽和内存预留余量，不能把资源用到 100% 才认为部署成功。
- 预分配 tensor 和图像 buffer，避免运行时反复申请释放。
- 将策略、相机、控制、日志和监控分线程或分进程，并定义优先级。
- 记录模型版本、归一化统计、相机标定、关节顺序、软件版本和硬件温度。
- 支持启动检查、健康检查、自动重启和原生策略回退。

## FlashRT 到底解决什么

根据 FlashRT 当前仓库的定位，它主要是实时 AI 推理运行时，重点优化：

- 手写或融合 CUDA 算子，减少内存访问和 Python 调度。
- CUDA Graph 和静态执行图，降低重复调度开销。
- FP8、NVFP4 等低精度路径，减少显存和计算成本。
- 针对部分 VLA 模型和 NVIDIA/AMD 硬件提供加速实现。
- 通过 Structures 只接管可以加速的算子，其余算子保留在主机侧。

因此它解决的是：

```text
模型 forward 更快
单次推理延迟更低
显存压力更小
边缘 GPU 更容易达到实时频率
```

它不能自动解决：

```text
相机采集和时间同步
网络传输
多线程调度
电机控制安全
急停和碰撞保护
模型异常与服务断开
长期运行监控
```

FlashRT README 中列出的 Pi0.5、GROOT、Pi0-FAST 等支持范围和 benchmark 不能直接推导出
当前 ACT checkpoint 一定兼容，也不能把模型推理频率直接当成机器人端到端控制频率。必须先
确认具体模型、权重格式、GPU 架构、CUDA 版本和 FlashRT 支持路径。

## 后续加速实施顺序

### 第一步：建立基线

固定模型、输入尺寸、相机数量、batch、动作 chunk 和硬件，记录：

```text
冷启动时间
预热后推理 P50/P95/P99
相机到动作端到端 P50/P95/P99
策略输出 Hz
GPU 显存峰值和余量
GPU/CPU 利用率
功耗、温度、连续运行时长
丢帧、队列欠载和异常次数
```

当前项目的远程异步方案可以作为网络基线，但真实部署还必须增加本机控制器和安全线程。

### 第二步：确认 FlashRT 兼容性

逐项确认：

1. 目标 VLA 是否在 FlashRT 当前支持列表中。
2. 权重格式是否支持，是否需要转换或校准。
3. GPU、驱动、CUDA 和编译器版本是否匹配。
4. 图像预处理、state 顺序、归一化统计和 action chunk 语义是否保持一致。
5. 低精度误差是否会改变抓取和放置动作。

### 第三步：做 A/B 对照

同一批固定观测分别通过原生实现和 FlashRT，比较：

- 动作最大绝对误差和平均误差。
- 单次推理和整段 action chunk 的延迟。
- 显存峰值、功耗和温度。
- 连续运行时是否出现显存增长、卡死、掉帧或输出异常。
- 仿真任务成功率，而不是只看 benchmark Hz。

### 第四步：接入本机安全执行

即使 FlashRT 达到目标频率，动作仍要经过本机安全层：

```text
FlashRT action
  -> 数值检查
  -> 关节位置/速度/加速度限幅
  -> 工作空间和碰撞检查
  -> watchdog 时间戳检查
  -> 低级控制器
```

FlashRT 进程崩溃、超时或 GPU 内存不足时，安全层应切换到停止/安全姿态/人工接管，不能
继续使用未确认的旧动作。

## 推荐的最终部署形态

### 开发和仿真阶段

可以继续使用：

```text
本机 Isaac Sim + 服务器 Policy Server + 异步 action chunk
```

重点验证模型行为、数据质量和网络容错。

### 真实机器人阶段

优先使用：

```text
机器人本机：相机 + 策略推理 + 安全层 + 低级控制
服务器：训练、checkpoint 管理、日志汇总和离线分析
```

只有在网络、带宽、时延和故障恢复经过验证时，才考虑远程策略推理。远程服务可以作为
高层策略或实验模式，但不应成为低级控制的唯一依赖。

## 当前项目的下一步

1. 保留现有 ACT 原生推理作为基线。
2. 选择 FlashRT 当前明确支持的 VLA 和硬件建立最小 A/B 测试。
3. 把 GPU、相机、队列、网络和 watchdog 指标统一记录。
4. 在仿真中注入掉帧、延迟、断网、服务重启和动作越界，验证安全降级。
5. 再决定 FlashRT 是否值得进入真实机器人本机推理链路。
