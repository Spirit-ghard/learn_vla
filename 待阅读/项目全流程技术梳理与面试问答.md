# LWH Robot Learning 项目全流程技术梳理与面试问答

> 这份文档面向当前项目的开发、排障和面试准备。目标不是记住几条启动命令，而是能够回答：数据从哪里来、每一帧代表什么、模型到底学了什么、训练结果为什么可能不好，以及如何用证据定位问题。
>
> 检查依据：当前仓库 `stage_5`、项目源码、当前本地数据和已经保存的 ACT checkpoint。文中涉及的当前样本统计来自 `datasets/hdf5/lwh_so101_table_test1_21episodes.hdf5` 和 `datasets/lerobot/so101_table_test1_21episodes`。

## 先记住结论

这个项目不是“启动 Isaac Sim，然后把模型接上去”这么简单。它是一条有多个数据契约的链路：

```text
IsaacLab 任务
    -> 遥操作输入
    -> HDF5 原始轨迹
    -> HDF5 数据审查
    -> LeRobotDataset v3
    -> ACT 训练与归一化统计
    -> Policy Server
    -> IsaacLab 异步客户端
    -> 闭环评估
```

最重要的四条原则：

1. **任务成功不等于训练成功。** 按 `N` 保存只能说明操作者认为成功，必须另外检查物体最终状态、轨迹完整性和闭环成功率。
2. **训练 loss 下降不等于策略会完成任务。** loss 只表示训练样本上的监督误差，不能代替回放和闭环评估。
3. **每个字段都必须有相同的顺序、单位、时间基准和图像语义。** `observation.state`、`action`、相机名称、关节顺序只要有一处错位，模型可能仍然能训练，但行为会错误。
4. **先验证数据和时钟，再调模型。** 绝大多数“模型效果不好”首先应该怀疑数据语义、相机输入、时间对齐、动作空间或初始状态，而不是马上增加训练步数。

## 1. 项目边界和版本

### 1.1 项目做什么

当前项目只面向仿真验证：

- IsaacLab 创建 SO101 桌面任务。
- 键盘或真实 SO101 Leader 作为输入，驱动仿真中的 follower。
- 录制 HDF5，回放 HDF5，检查轨迹和传感器。
- 将 HDF5 转为 LeRobotDataset v3。
- 使用 LeRobot 训练 ACT 等策略。
- 在服务器运行 LeRobot Policy Server，本地 Isaac Sim 运行异步客户端。
- 当前不控制真实 follower。`so101leader` 模式只读取真实 Leader，作为仿真输入。

## 2. 面试题一：请你在一分钟内介绍项目

### 问题

请你介绍这个项目的目标、数据流和你负责的关键技术点。

### 合格回答

这是一个以 IsaacLab 为仿真基础、以 LeRobot 为训练端的 SO101 机器人学习流程。任务使用 IsaacLab Manager-Based 环境，通过 Gym task id 注册自定义桌面任务。遥操作端既支持 Carb 键盘，也支持读取真实 SO101 Leader 的 6D 关节位置；真实 follower 不参与控制。

数据先在 IsaacLab 中按 episode 录制为 HDF5，HDF5 保存训练需要的关节状态、动作、front/wrist 图像、timestamp 和 episode 元信息，同时保存机器人与物体状态用于回放验证。转换脚本读取成功且有效的 episode，生成 LeRobotDataset v3 的 Parquet、图像或视频、`info.json`、`stats.json` 和任务表。训练时 ACT 输入双相机和 6D state，输出 6D joint position action，并通过归一化统计完成预处理。

部署时把 LeRobot PolicyServer 放到服务器，把 IsaacLab 环境留在本机。客户端异步发送最新 observation，服务端返回多步 action chunk，本地 action queue 在 30 Hz 消费动作，仿真以 60 Hz 运行，从而把网络等待从仿真主循环中移出。排障上，我会先检查数据契约、动作单位、时间戳、相机输入和回放，再看 loss 和闭环成功率。

### 面试官想听到什么

- 你知道环境、数据、训练、推理各自的边界。
- 你知道 `state/action` 的单位和关节顺序不是“默认就对”。
- 你区分了训练损失、离线预测误差和闭环任务成功率。
- 你能解释为什么远程推理要返回 action chunk，而不是一帧一请求。
- 你知道当前方案适合仿真验证，真实机器人需要更严格的边缘侧安全闭环。

## 3. 架构和进程边界

### 3.1 单进程仿真端

任务和通用入口分离：

```text
任务模块
  定义 robot / scene / action / observation / reset / termination
  gym.register("Lwh-SO101-Table-v0")

通用入口
  AppLauncher
  导入任务注册模块
  parse_env_cfg(task)
  env_cfg.use_teleop_device(device)
  gym.make(task, cfg=env_cfg)
  teleop.advance() -> env.step(action)
```

任务注册位于 [`source/lwh_isaaclab_tasks/lwh_isaaclab_tasks/tasks/so101_table/__init__.py`](../source/lwh_isaaclab_tasks/lwh_isaaclab_tasks/tasks/so101_table/__init__.py)。注册时 entry point 仍然是 IsaacLab 的 `ManagerBasedRLEnv`，具体配置通过 `env_cfg_entry_point` 传入。这是“用配置组合任务”，不是修改 IsaacLab 环境基类。

### 3.2 本地和服务器的边界

```text
本机 Isaac Sim / IsaacLab
  - 创建场景
  - 运行物理和渲染
  - 取得 joint state、front、wrist
  - 异步发送 observation
  - 接收 action chunk
  - 执行 env.step(action)

服务器 LeRobot 环境
  - 加载 checkpoint
  - 按训练配置预处理输入
  - ACT 推理
  - 返回多步 action chunk
```

本机不会加载服务器上的模型文件。服务器也不需要创建 Isaac Sim 环境。两端通过 [`services.proto`](../source/lwh_isaaclab_tasks/lwh_isaaclab_tasks/policy/transport/services.proto) 对齐消息结构。

### 3.3 为什么不能只看 GPU 利用率

GPU 利用率只是某个时间窗口内 GPU 是否有工作，不能证明系统满足实时性。端到端延迟可能来自：

- 相机渲染和图像拷贝。
- CPU 上的 NumPy 转换和 pickle 序列化。
- 网络上传和 SSH 加密。
- 服务端排队。
- 模型推理。
- action chunk 返回后主线程的调度。

因此应该同时测量：`wall_hz`、policy queue 长度、underflow、观测上传耗时、chunk 端到端耗时、服务端推理耗时、显存和连续运行稳定性。

## 4. IsaacLab 任务环境

### 4.1 场景组成

主要配置在 [`so101_table_env_cfg.py`](../source/lwh_isaaclab_tasks/lwh_isaaclab_tasks/tasks/so101_table/so101_table_env_cfg.py)：

- `robot`：项目内置 `so101_follower.usd`。
- `table`：桌面碰撞体和可视材质。
- `banana`：当前 scene key 仍叫 `banana`，兼容旧脚本；实际场景资产和任务历史可能有香蕉/棍子版本差异，必须以当前分支文件和录制元数据为准。
- `placement_box_*`：托盘底板和四面边缘。
- `ground`：可选大地面，遥操作默认可以移除。
- `light`：Dome light。
- `front`：固定在 robot base 的手外相机。
- `wrist`：挂在 robot gripper 下的腕部相机。
- `overview`：固定在世界中的观察相机，只用于人工观察和 HDF5 可视化，不进入默认训练输入。

### 4.2 场景配置和资产配置的职责

项目已经把任务相关的具体数值放到环境配置的顶部，例如：

```python
wrist_camera_pos = (...)
front_camera_pos = (...)
overview_camera_pos = (...)
camera_width = 640
camera_height = 480
camera_update_period = 1 / 30.0
robot_initial_joint_pos = {...}
object_init_pos = (...)
placement_box_center = (...)
```

资产模块 [`assets/so101.py`](../source/lwh_isaaclab_tasks/lwh_isaaclab_tasks/assets/so101.py) 负责可复用的机器人 USD 和 articulation 配置；任务环境负责“本任务把机器人放在哪里、物体放在哪里、相机在哪里”。面试时要能解释这个边界：资产提供默认能力，任务决定具体实验条件。

### 4.3 观测项不等于训练输入

当前 policy observation group 中包含：

```text
joint_pos
joint_vel
joint_pos_rel
joint_vel_rel
actions
wrist
front
overview
ee_frame_state
joint_pos_target
```

这些是 IsaacLab 环境可提供的观察项。转换脚本和异步客户端只选择训练契约中的：

```text
observation.state       -> 6D joint position
observation.images.front
observation.images.wrist
action                  -> 6D joint position target
```

所以“环境里有 overview”不会自动导致 overview 被模型使用。真正决定训练输入的是 LeRobotDataset 的 `meta/info.json` 和 checkpoint 的 `input_features`。

### 4.4 reset 和轻微随机化

当前 reset 事件包括：

- 恢复场景默认状态。
- 恢复机器人默认关节目标。
- 对可抓取物体做小范围 XY 随机化，当前配置约为 `x/y ±0.03 m`。

域随机化的目的不是把任务变得随机到无法完成，而是避免策略只记住单一像素位置。随机化必须满足：

- 所有位置仍在相机视野和机器人可达范围内。
- 不与托盘或机器人初始姿态重叠。
- 训练、回放和评估时明确知道是否启用。
- 记录随机化后的初始状态，否则无法复现实验。

## 5. 面试题二：控制频率、渲染频率和相机 FPS 有什么区别

### 问题

你说系统控制 60 Hz、相机 30 FPS、Isaac Sim 窗口 FPS 可能只有 32，这三个数字分别是什么意思？

### 标准回答

- **控制频率**：主循环多久执行一次 `env.step(action)`。当前任务设置 `sim.dt=1/60`、`decimation=1`，目标控制频率约为 60 Hz。
- **相机 FPS**：相机多久生成一张新图。`update_period=1/30` 表示相机数据目标为 30 Hz。
- **渲染频率**：Kit/viewport 产生新画面的频率，受 GPU、窗口、相机数量和 UI 影响。
- **wall loop Hz**：从真实墙钟时间看，程序循环实际跑了多少次。它是系统性能结果，不是配置目标。

如果控制循环 60 Hz、相机 30 Hz，那么两个连续 physics step 可能使用同一张相机图像，但机器人动作仍然每步更新。若 wall loop 只有 32 Hz，说明主循环实际无法兑现 60 Hz，必须查看是渲染、物理、CPU、数据拷贝还是等待逻辑造成的。

### 为什么 VLA/ACT 不一定需要 60 FPS 图像

操作任务通常更需要：

- 清晰的物体边界。
- 稳定的相机曝光和视角。
- action 与 observation 时间对齐。
- 足够覆盖抓取、抬升、移动、放置、松爪、撤离各阶段的数据。

`640x480 @ 30 FPS` 是本项目的合理目标，但前提是**实际采集时间间隔接近 33 ms**。如果真实采集只有 17 Hz，却把元数据标成 30 Hz，问题不是“30 还是 60”的选择，而是时间标签与样本间隔不一致。

## 6. 遥操作和动作空间

### 6.1 键盘模式：8D IK action

键盘设备产生的是相对末端控制和相对关节/夹爪控制，当前入口把它整理成 8 维动作，交给 Differential IK 和 RelativeJointPosition action term。它适合交互式控制，但它的输出不是 SO101 的 6 个关节目标。

因此：

- 键盘录制得到的是 8D IK action 语义。
- 不能直接把键盘数据当成 6D joint-position action 训练。
- 如果要训练当前的 SO101 ACT 策略，应使用 `--teleop_device so101leader`。

### 6.2 Leader 模式：6D joint position action

Leader 模式读取真实 Leader 的校准后位置，按以下顺序转换为仿真弧度：

```text
0 shoulder_pan
1 shoulder_lift
2 elbow_flex
3 wrist_flex
4 wrist_roll
5 gripper
```

单位是仿真使用的弧度或关节位置目标。这个动作空间与当前 LeRobotDataset 和 ACT checkpoint 的输出一致：`shape=(6,)`。

### 6.3 标定为什么会影响训练

标定不是只影响真实机械臂。Leader 的原始电机位置必须经过：

- 电机 ID 对应。
- homing offset。
- range min/max。
- 正负方向。
- 归一化位置到仿真关节弧度的映射。

如果同一条数据中一部分 episode 使用了不同标定文件，数据看起来仍然是 6 维浮点数，但相同的手臂姿态可能对应不同的 action，模型会学习到互相冲突的监督信号。

检查入口：

```bash
conda activate lerobot05
cd /home/a/lwh_code/lwh_robot_learning
python3 scripts/calibrate_so101.py --arm leader --inspect
```

运行时可以用 [`scripts/inspect_so101_zero_pose.py`](../scripts/inspect_so101_zero_pose.py) 对比默认关节、当前关节、目标关节和 Leader 映射值。标定解析顺序见 [`scripts/calibrate_so101.py`](../scripts/calibrate_so101.py)：显式参数、环境变量、项目 `configs`、LeRobot cache，再到历史 LeIsaac cache。

### 6.4 遥操作的正式启动

```bash
conda activate isaac
cd /home/a/lwh_code/lwh_robot_learning
python3 scripts/teleop.py \
  --task Lwh-SO101-Table-v0 \
  --num_envs 1 \
  --teleop_device so101leader \
  --leader_port /dev/ttyACM0 \
  --camera_mode dual
```

正式录制：

```bash
python3 scripts/teleop.py \
  --record \
  --task Lwh-SO101-Table-v0 \
  --num_envs 1 \
  --teleop_device so101leader \
  --leader_port /dev/ttyACM0 \
  --camera_mode dual \
  --output datasets/hdf5/so101_table_raw.hdf5
```

episode 生命周期：

```text
B       开始当前 episode
N       以 success 保存当前 episode，然后 reset
R       以 failure 结束并废弃当前 episode，然后 reset
Ctrl+C  安全退出；未用 N/R 正常结束的当前 episode 废弃
```

`--overwrite` 会删除同名输出；不传 `--overwrite` 且不传 `--append` 时，输出会自动使用 `_01`、`_02` 等后缀。原始 HDF5 应当保留，不要用网页删除功能直接修改唯一原件。

## 7. HDF5 数据格式

### 7.1 根目录结构

本项目 HDF5 根目录为：

```text
/data
/episodes
/metadata
```

episode 主数据位于：

```text
/data/demo_0
/data/demo_1
...
```

`/episodes/000000` 是指向 `/data/demo_0` 的硬链接。它不是另一份数据，不应把两个路径下的 episode 重复计数。

### 7.2 metadata

`/metadata` 保存整个文件的契约：

```text
attrs:
  format                 lwh_isaaclab_hdf5_v1
  task                   Lwh-SO101-Table-v0
  fps                    30
  action_dim             6
  teleop_device          so101leader
  camera_keys            [front, wrist]
  training_camera_keys   [front, wrist]
  visualization_camera_keys []
  joint_names            [6 个关节名称]
  render_config           JSON 字符串

datasets:
  camera_keys
  training_camera_keys
  visualization_camera_keys
  joint_names
```

同一信息同时写成 attribute 和 string dataset，是为了兼容不同的读取方式。使用时优先读 string dataset，旧文件再回退到 JSON attribute。

### 7.3 每个 episode 的属性

```text
/data/demo_0.attrs:
  episode_index
  task
  teleop_device
  success
  valid
  num_samples
  outcome
  started_unix_ns
  ended_unix_ns
  duration_s
  camera_keys
  training_camera_keys
  visualization_camera_keys
  joint_names
```

`success` 是操作者按 `N` 后写入的标记；`valid` 表示达到最少帧数并被正式结束。二者都不是自动物理成功判定。

### 7.4 每一帧的核心字段

```text
observation/state                    float32, (6,)
observation/joint_pos                float32, (6,)
observation/joint_vel                float32, (6,)
observation/joint_pos_rel            float32, (6,)
observation/joint_vel_rel            float32, (6,)
observation/joint_pos_target         float32, (6,)
observation/ee_frame_state            float32, (7,)
observation/actions                  float32, (6,)

observation/images/front              uint8, (480, 640, 3)
observation/images/wrist              uint8, (480, 640, 3)
observation/images/overview           uint8, (480, 640, 3), 仅 triple 时存在

action                                float32, (6,) 或键盘模式下对应动作维度
actions                               action 的兼容别名
timestamp                             float64, 秒
frame_index                           int64
episode_index                        int64
task                                  UTF-8 字符串
```

另外保存了回放和分析用的环境状态：

```text
observation/env_state/robot_joint_position
observation/env_state/robot_joint_velocity
observation/env_state/banana_root_pose
observation/env_state/banana_root_velocity
observation/env_state/object_root_pose
observation/env_state/object_root_velocity
```

这些环境状态默认不会被转换进训练数据。它们的价值是回答“动作执行后机器人和物体到底发生了什么”。

episode 初始状态位于：

```text
initial_state/articulation/robot/root_pose
initial_state/articulation/robot/joint_position
initial_state/articulation/robot/joint_velocity
initial_state/rigid_object/banana/root_pose
initial_state/rigid_object/banana/root_velocity
```

回放用它恢复录制起点，避免每次从当前默认场景开始导致轨迹对不上。

### 7.5 最容易错的语义：state 和 action 的时序

当前 [`record_hdf5.py`](../scripts/record_hdf5.py) 的主循环逻辑是：

```text
action = teleop.advance()
observations = env.step(action)
append_frame(observations, action)
```

因此当前文件里保存的 `observation/state[t]` 更接近“执行 `action[t]` 之后得到的状态”，而不是严格的“执行动作前状态”。这会形成一个潜在的一步时间偏移：

```text
理想监督关系：state[t] -> action[t]
当前实现更接近：state_after_action[t] -> action[t]
```

对于动作缓慢、控制目标是位置的任务，影响可能不明显；但对快速接触、夹爪闭合、放置动作，偏移可能导致模型学到滞后的控制关系。面试官如果问“如何保证 state-action 对齐”，必须明确回答这个实现细节，而不是只说“字段都在同一帧”。

改进方向：

1. 在 `env.step(action)` 前保存发送动作前的 observation，并把它与即将执行的 action 配对。
2. 如果需要保存执行后的状态，另存为 `observation/state_after`，不要覆盖训练语义。
3. 修改后重新转换数据，不要把新旧语义混在同一个数据集。

### 7.6 时间戳的真实含义

录制器使用 `time.perf_counter()` 记录相对时间，所以 HDF5 的 timestamp 反映采集进程的墙钟时间。它不是仿真内部的理论时间，也不是由 `fps` 计算出来的。

但是当前录制器把 metadata 的 `fps` 固定写为 30。这个字段表示训练和转换期望的采样率，不保证实际主循环已经达到 30 Hz。因此必须同时检查：

```text
实际平均采样率 = (帧数 - 1) / (最后 timestamp - 第一 timestamp)
```

不能只看 `metadata.attrs["fps"]`。

## 8. 从 HDF5 转换为 LeRobotDataset v3

转换入口是 [`scripts/convert_hdf5_to_lerobot.py`](../scripts/convert_hdf5_to_lerobot.py)。它运行在 LeRobot 环境，不在 Isaac Sim 环境。

### 8.1 转换器当前做了什么

转换流程可以概括为：

```text
打开 HDF5
  -> 找到 /data 或 /episodes
  -> 选择 episode
  -> 读取 state/action/image 样本推断 features
  -> LeRobotDataset.create(...)
  -> 每帧 dataset.add_frame(frame)
  -> 每个 episode dataset.save_episode()
  -> dataset.finalize()
```

默认规则：

- 只转换 `success=True` 的 episode。
- 跳过每个 episode 开头 5 帧。
- 默认读取 HDF5 的 `training_camera_keys`。
- 常规双相机为 `front,wrist`。
- `overview` 默认不进入训练数据。
- 默认输出 `image` 格式，避免当前环境部分视频解码链路问题。

### 8.2 常用转换命令

```bash
conda activate lerobot05
cd /home/a/lwh_code/lwh_robot_learning

python3 scripts/convert_hdf5_to_lerobot.py \
  --input datasets/hdf5/lwh_so101_table_test1_21episodes.hdf5 \
  --repo_id lwh/so101_table \
  --output_dir datasets/lerobot/so101_table \
  --overwrite
```

只转换 front：

```bash
python3 scripts/convert_hdf5_to_lerobot.py \
  --input datasets/hdf5/so101_table_raw.hdf5 \
  --repo_id lwh/so101_table_front \
  --output_dir datasets/lerobot/so101_table_front \
  --camera_keys front \
  --overwrite
```

双相机：

```bash
python3 scripts/convert_hdf5_to_lerobot.py \
  --input datasets/hdf5/so101_table_raw.hdf5 \
  --repo_id lwh/so101_table_dual \
  --output_dir datasets/lerobot/so101_table_dual \
  --camera_keys front,wrist \
  --overwrite
```

把所有 episode 纳入转换筛选：

```bash
python3 scripts/convert_hdf5_to_lerobot.py \
  --input datasets/hdf5/so101_table_raw.hdf5 \
  --repo_id lwh/so101_table_all \
  --output_dir datasets/lerobot/so101_table_all \
  --episodes all \
  --include_invalid \
  --overwrite
```

注意：`--episodes all` 只放宽 success 筛选；如果 episode 的 `valid=False`，仍需要 `--include_invalid` 才会纳入。失败数据一般只用于调试，不建议直接加入正式训练集。

### 8.3 每个转换参数的意义

| 参数 | 作用 | 使用判断 |
| --- | --- | --- |
| `--input` | 原始 HDF5 | 必须是本项目录制格式或兼容结构 |
| `--repo_id` | LeRobot 数据集标识 | 本地也必须填写，影响 metadata |
| `--output_dir` | 数据集落盘目录 | 推荐显式指定，便于训练复现 |
| `--camera_keys` | 覆盖相机选择 | 只能选择 HDF5 中真实存在的流 |
| `--episodes successful/all` | 成功 episode 或全部 | 正式训练一般使用 successful |
| `--include_invalid` | 纳入 invalid episode | 调试时使用，正式训练慎用 |
| `--skip_first_frames` | 每段开头跳过的帧数 | 去掉启动后静止过渡；不能盲目过大 |
| `--action_key` | HDF5 动作路径 | 默认 `action`，旧数据可指定其他路径 |
| `--image_format image/video` | 图片文件或视频特征 | 当前环境优先 image，视频要确认 decoder |
| `--image_writer_threads` | 图片写入线程 | 影响转换速度，不改变数据语义 |
| `--overwrite` | 删除已有输出目录 | 重新转换前使用，注意先备份 |
| `--dry_run` | 只检查 schema/features | 正式转换前推荐先用 |

### 8.4 一个关键事实：当前转换器没有做时间重采样

LeRobot 的 `LeRobotDataset.add_frame()` 如果没有收到 `timestamp`，会自动使用：

```text
timestamp = frame_index / dataset.fps
```

当前转换器构造 frame 时只放入：

```text
observation.state
action
task
observation.images.front
observation.images.wrist
```

没有把 HDF5 的原始 `timestamp` 传给 `dataset.add_frame()`。因此当前转换的行为是：

- 按 HDF5 帧的顺序复制样本。
- 按目标 `fps` 重新标注均匀时间戳。
- 不会基于原始 timestamp 插值、丢帧或补帧。

这在原始采集已经稳定接近目标 FPS 时可以接受；如果实际采集频率明显偏低或抖动，应该先修录制频率或写时间感知转换器。不能把 `--fps 30` 当成“已经把 17 Hz 数据变成了 30 Hz”。

### 8.5 转换前的最小检查

先只看转换计划：

```bash
python3 scripts/convert_hdf5_to_lerobot.py \
  --input datasets/hdf5/lwh_so101_table_test1_21episodes.hdf5 \
  --repo_id lwh/so101_table_check \
  --output_dir datasets/lerobot/so101_table_check \
  --dry_run
```

重点确认输出中的：

- episode 数量是否符合预期。
- state/action shape 是否都是 `(6,)`。
- 相机是否为 `front,wrist`。
- image shape 是否是 `(480,640,3)`。
- `skip_first_frames` 后是否还剩足够帧数。
- 是否意外把失败或 invalid episode 纳入。

## 9. LeRobotDataset v3 的目录和字段

### 9.1 目录结构

典型 v3 数据集如下：

```text
so101_table/
├── data/
│   └── chunk-000/
│       ├── file-000.parquet
│       └── ...
├── meta/
│   ├── info.json
│   ├── stats.json
│   ├── tasks.parquet
│   └── episodes/
│       └── chunk-000/file-000.parquet
├── videos/
│   ├── observation.images.front/
│   │   └── chunk-000/file-000.mp4
│   └── observation.images.wrist/
│       └── chunk-000/file-000.mp4
└── README.md  # 可选
```

如果使用 `--image_format image`，图像可能以逐帧图片路径的形式存在；如果使用 `video`，视频特征会写入 `videos/`，Parquet 保存相应的视频路径和时间信息。

### 9.2 `info.json`

当前训练数据的核心信息：

```json
{
  "codebase_version": "v3.0",
  "robot_type": "so101_follower",
  "total_episodes": 21,
  "total_frames": 3623,
  "fps": 30,
  "features": {
    "observation.state": {"dtype": "float32", "shape": [6]},
    "action": {"dtype": "float32", "shape": [6]},
    "observation.images.front": {"dtype": "image", "shape": [480, 640, 3]},
    "observation.images.wrist": {"dtype": "image", "shape": [480, 640, 3]}
  }
}
```

`info.json` 是数据契约索引。它应该与 checkpoint 的 `input_features` 对得上。检查模型时要看 checkpoint 里的 `config.json`，不要只看命令行里写了什么。

### 9.3 `stats.json` 和归一化

LeRobot 会为 state、action 和视觉特征保存统计量。当前 ACT checkpoint 使用：

```text
STATE  -> MEAN_STD
ACTION -> MEAN_STD
VISUAL -> MEAN_STD
```

对 state/action，典型过程是：

```text
x_normalized = (x - mean) / std
```

推理输出再使用相同统计量反归一化回仿真关节目标。若使用了错误数据集的 `stats.json`、错误关节顺序或错误单位，模型输出可能数值有限但物理动作完全不对。

当前训练数据 state 的名称顺序为：

```text
shoulder_pan
shoulder_lift
elbow_flex
wrist_flex
wrist_roll
gripper
```

### 9.4 `tasks.parquet`

任务文本在转换时写入 frame 的 `task` 字段，LeRobot 将其映射到 `task_index` 和 `tasks.parquet`。当前默认任务描述是：

```text
Move the rod into the placement tray.
```

如果实际场景已经换成香蕉，建议新数据使用准确且一致的任务描述，例如：

```text
Pick up the banana and place it into the tray.
```

单任务训练时不要让同一数据集的文本描述一会儿是 rod、一会儿是 banana，除非你确实希望训练多任务条件策略。

### 9.5 双相机和 overview 的关系

训练数据应当是：

```text
observation.images.front
observation.images.wrist
```

overview 只为人工观察服务：

```text
Isaac Sim / HDF5 viewer 可以显示 overview
LeRobot converter 默认不选 overview
Policy client 不发送 overview
ACT checkpoint 没有 overview input feature
```

只要 `info.json`、checkpoint `config.json` 和 client 的 observation schema 都没有 overview，就不会把主视角误送进模型。

## 10. ACT 训练到底在优化什么

### 10.1 当前 ACT 配置

当前保存的 `checkpoints/act_so101_table_030000/train_config.json` 记录：

| 配置 | 当前值 |
| --- | ---: |
| policy | ACT |
| state 输入 | 6 维 |
| 图像输入 | front + wrist |
| 图像尺寸 | `3x480x640`，进入模型前为 CHW |
| vision backbone | ResNet18 |
| `dim_model` | 512 |
| `n_encoder_layers` | 4 |
| `n_decoder_layers` | 1 |
| `use_vae` | true |
| `kl_weight` | 10.0 |
| `chunk_size` | 100 |
| `n_action_steps` | 100 |
| batch size | 32 |
| workers | 8 |
| AMP | true |
| optimizer | AdamW |
| learning rate | `1e-5` |
| weight decay | `1e-4` |
| steps | 30000 |
| save frequency | 5000 |

这里的 `chunk_size=100` 表示一次模型预测一段动作序列，而不是仿真控制频率。30 FPS 下 100 个动作理论上覆盖约 3.33 秒。

### 10.2 ACT 的监督信号

当前 LeRobot 0.5.1 的 ACT forward 逻辑是：

```text
actions_hat, latent = model(batch)
l1_loss = masked L1(batch[action], actions_hat)
if use_vae:
    loss = l1_loss + kl_weight * kld_loss
else:
    loss = l1_loss
```

动作 padding 会被 mask 掉，不参与 L1 损失。`use_vae=true` 时，打印的总 loss 还包含 KL 项，所以不能把总 loss 直接当作动作平均误差。

源代码位置：

```text
/home/a/lerobot_05/src/lerobot/policies/act/modeling_act.py
```

### 10.3 训练日志字段怎么读

典型日志：

```text
step:5K smpl:150K ep:872 epch:41.51
loss:0.150 grdn:13.743 lr:1.0e-05
updt_s:0.258 data_s:0.032
```

| 字段 | 含义 | 如何判断 |
| --- | --- | --- |
| `step` | optimizer 更新次数 | 与 `steps` 比较进度 |
| `smpl` | 已处理样本数的日志展示 | 不等于 episode 数 |
| `epch` | 经过的数据集轮数近似 | 结合数据量看是否过拟合 |
| `loss` | 当前训练 loss，ACT 可能含 KL | 观察趋势和波动，不单看一个点 |
| `grdn` | 梯度范数 | 长期爆炸或频繁裁剪要检查 |
| `lr` | 当前学习率 | 确认没有意外为 0 或过大 |
| `updt_s` | 一次模型更新耗时 | 主要看 GPU/模型计算 |
| `data_s` | 一次取数据耗时 | 过大说明数据读取瓶颈 |

### 10.4 loss 应该怎样解释

不同数据集、归一化方式、模型配置的 loss 数值不能直接横向比较。更可靠的判断是：

- 同一实验内 loss 是否从高值下降并趋于稳定。
- 是否出现 NaN、突然尖峰或周期性抖动。
- checkpoint 之间闭环表现是否改善。
- 训练 loss 很低时，固定样本上的动作预测是否接近标签。
- 是否存在 train loss 下降但闭环成功率下降的过拟合。

当前 ACT 使用 VAE，训练输出的 `loss` 是 `L1 + 10 * KL`。要研究动作误差，应在评估脚本中分别记录动作 L1/MAE，而不是只看训练终端的一列总 loss。

## 11. 如何查看一次训练是否正常

### 11.1 训练前检查

确认：

```text
数据集 total_episodes 与预期一致
total_frames > 0
fps 与采集目标一致
state/action shape 一致
front/wrist 都存在
图像 dtype/shape 正确
tasks.parquet 内容一致
stats.json 存在且没有空 std
```

训练输入检查：

```text
dataset info features
checkpoint input_features
policy output_features
client raw observation schema
```

这四处应该形成闭环：

```text
HDF5 state/action
  == LeRobot state/action
  == checkpoint input/output
  == Isaac client state/action
```

### 11.2 训练中检查

至少保存：

- 命令行完整参数。
- `train_config.json`。
- `config.json`。
- 每个 checkpoint 的模型、preprocessor、postprocessor 和 stats。
- 训练日志。
- 数据集 `info.json`、`stats.json`。
- 训练时的 git commit 和环境版本。

观察：

1. `loss` 是否整体下降。
2. `grdn` 是否出现异常尖峰。
3. `updt_s` 和 `data_s` 谁占主要时间。
4. 是否频繁 OOM、worker 崩溃、视频解码失败。
5. checkpoint 是否按预期保存。

### 11.3 训练后检查

不能直接用“最后一个 checkpoint”。应至少比较：

```text
005000
010000
015000
020000
025000
030000
```

对每个 checkpoint 做同样的固定评估：

- 同一批固定 observation 的 action 误差。
- 同样初始状态的 IsaacLab 闭环运行。
- 同样的随机种子和 episode 数。
- 成功率、完成阶段、碰撞、放置误差、动作抖动。

如果 30000 step 的 loss 更低但闭环不如 15000 step，优先考虑过拟合、数据分布或动作时间尺度，而不是继续训练到更大步数。

### 11.4 当前训练实例的读取方式

当前 checkpoint：

```text
checkpoints/act_so101_table_030000/
```

训练配置：

```text
checkpoints/act_so101_table_030000/train_config.json
```

已保存的远端完整训练目录：

```text
/home/a/lwh_code/lwh_lerobot_data/runs/act_video_b32_50k_20260823_184025/
```

虽然目录名包含 `50k`，checkpoint 内的配置明确写的是 `steps=30000`。面试时要以 checkpoint 内的 `train_config.json` 为准，不以目录名猜测。

## 12. 数据清洗和数据集设计

### 12.1 原始数据、清洗数据和训练数据要分层

建议保留三层目录：

```text
datasets/hdf5/raw/       原始采集，只读保存
datasets/hdf5/clean/     按 episode 筛选后的 HDF5 或记录清单
datasets/lerobot/        用于训练的 v3 数据集
```

当前项目可以用网页删除 episode，但它会直接修改 HDF5。使用前先复制原文件：

```bash
cp datasets/hdf5/so101_table_raw.hdf5 datasets/hdf5/so101_table_raw_backup.hdf5
```

原始文件的意义是保留证据：以后发现清洗规则错了，可以重新生成训练集。

### 12.2 episode 级清洗

优先删除整个 episode，而不是随机删中间帧。检查项目：

| 项目 | 合格标准 |
| --- | --- |
| 任务 | 与当前 task 和 task text 一致 |
| 起点 | 机器人、物体、相机状态正常 |
| 过程 | 包含接近、抓取、搬运、放置、松爪和撤离的完整阶段 |
| 结尾 | 操作确实完成，不是刚抓住就按 N |
| 失败 | 没抓住、飞出、严重碰撞、遮挡、卡死应剔除 |
| 相机 | front/wrist 同时存在且画面非空白 |
| 动作 | 没有 NaN、Inf、明显跳变或长期饱和 |
| 时间 | timestamp 单调，间隔没有长时间断裂 |
| 标定 | 所有 episode 使用同一套关节顺序和映射 |

### 12.3 帧级清洗的原则

不要对轨迹中间帧做随机删除，因为 ACT 依赖连续时间结构。可做的操作：

- 去掉连续的启动静止帧。
- 去掉连续的结束后等待帧。
- 裁掉明确的录制前后无效区间。
- 对确定损坏的连续区间，整个 episode 直接剔除通常更稳妥。

如果必须裁剪帧，必须同步裁剪所有模态：

```text
state
action
front
wrist
timestamp
frame_index
episode_index
```

不能只删图像而保留 action，也不能只删 action 而保留图像。

### 12.4 图像质量清洗

图像清晰度不是“越大越好”，而是要服务于识别和控制。检查：

- 物体在 front 中是否占据足够像素。
- wrist 是否能看到夹爪和接触区域。
- 是否有运动模糊、严重曝光、全黑、全灰、画面冻结。
- 两路相机是否与训练时的位置和朝向一致。
- 训练和推理的 resize、颜色通道、dtype 是否一致。

如果 front 图像拍不到托盘，模型就不可能可靠地学会“把东西放到托盘里”，即使 state/action 看起来全部正确。

### 12.5 动作连续性清洗

对每个 episode 计算：

```text
delta_action[t] = action[t] - action[t-1]
```

关注：

- 每个关节的最大绝对跳变。
- 95/99 分位数。
- 是否大量贴在 joint limit。
- gripper 是否有清晰的开、闭、保持阶段。
- action 是否长时间完全不变。
- state 与 action 是否相差异常大。

动作跳变可能来自：Leader 读取抖动、串口丢帧、标定切换、录制循环阻塞或数据拼接错误。

### 12.6 时间清洗

对每个 episode 计算：

```text
dt[t] = timestamp[t] - timestamp[t-1]
measured_fps = (N-1) / (timestamp[-1] - timestamp[0])
```

检查：

- `dt > 0`。
- 中位数是否接近目标周期。
- P95/P99 是否有明显长尾。
- 是否存在长时间卡顿。
- 两路相机是否与状态在同一采样节奏下写入。

如果 measured FPS 和 metadata FPS 不一致，要么修录制，要么在转换阶段明确重采样，不要静默忽略。

### 12.7 数据多样性和数据量

数据量不是只看 episode 数：

- 同一个人、同一个起点、同一个速度录 50 次，可能只是重复数据。
- 少量但覆盖不同 XY 起点、抓取角度、接触状态的数据，可能比大量重复轨迹更有效。
- 但随机化不能破坏任务语义，也不能让目标超出相机视野。

建议先收集少量高质量完整轨迹跑通，再增加：

1. 物体初始 XY 小范围变化。
2. 机器人初始姿态的小范围变化。
3. 抓取接触和放置角度变化。
4. 不同但仍然成功的运动速度。

## 13. 训练效果不好时的排查树

### 13.1 第一层：程序是否真的在用正确数据

先问：

```text
训练命令指向的是哪个 root？
repo_id 与 root 是否对应？
info.json 是否是当前数据？
checkpoint 是否是当前训练产生的？
是否误用了旧的 front-only 数据？
是否误用了键盘 8D 数据？
```

最常见的问题是目录名相近但内容不同。

### 13.2 第二层：输入输出契约

逐项对比：

```text
数据集 state shape       == (6,)
checkpoint state shape    == (6,)
client state shape        == (6,)

数据集 action shape       == (6,)
checkpoint action shape   == (6,)
client action shape       == (6,)

joint_names 顺序完全一致
state/action 单位一致
front/wrist 名称一致
图像 HWC/CHW 转换正确
RGB/BGR 没有反
```

只要其中一项失败，就先修数据契约，不调学习率。

### 13.3 第三层：数据是否包含完整任务

症状：模型会抓，但不会放。

优先检查：

- episode 是否真的包含放置和松爪阶段。
- 录制结束是否太早。
- `N` 是否在抓住后立即按下。
- 托盘是否在 front 画面中可见。
- wrist 是否能看到物体是否仍被夹住。
- 失败/半成功轨迹是否混进成功集。
- 物体最终状态是否真的在盒子范围内，而不是只看动作曲线。

### 13.4 第四层：时间和动作对齐

检查：

- HDF5 实际 measured FPS。
- LeRobot `info.json` FPS。
- client 的 `policy_hz`。
- action chunk 长度。
- 当前录制器是否保存了 step 后 state 与当前 action。
- 是否存在重复相机帧或长时间相同图像。

如果数据实际 17 Hz、训练标注 30 Hz、推理又按 30 Hz 执行，策略会以错误的时间尺度播放示教轨迹。抓取阶段可能仍然成功，因为抓取是局部动作；长时间的搬运和放置阶段更容易被压缩、提前结束或漂移。

### 13.5 第五层：模型是否过拟合或欠拟合

| 现象 | 可能原因 | 下一步 |
| --- | --- | --- |
| train loss 高且不降 | 学习率、数据损坏、输入契约、显存/AMP 问题 | 看 NaN、梯度、固定样本预测 |
| train loss 降不稳 | 数据读取、视频解码、batch 太小、动作标签冲突 | 先用 image 格式和少量数据复现 |
| train loss 很低，闭环差 | 过拟合、数据时间错、初始状态变了、相机视角变了 | 固定样本预测 + raw replay + 闭环 |
| 训练集表现好，新位置失败 | 多样性不足，策略记住了像素位置 | 增加小范围随机化和不同成功轨迹 |
| 所有 checkpoint 都差 | 契约、标定、相机、动作空间或场景问题 | 回到数据和执行链路 |
| 早期 checkpoint 好，后期变差 | 过拟合或训练集标签冲突 | 选最佳 checkpoint，不盲目最后一步 |

### 13.6 第六层：推理运行时

客户端日志重点看：

```text
实际循环 wall_hz
动作块数量
队列长度
队列欠载 underflows
观测上传延迟
动作块延迟
最近错误
```

判定：

- `underflows` 持续增加：动作供给不足，先看网络、chunk 长度和策略服务。
- queue 长期为 0：异步预取没有跟上，或服务端没有返回动作。
- wall_hz 低但 queue 正常：仿真/渲染慢，不一定是推理慢。
- server inference 很快但 upload 很慢：瓶颈在双相机序列化和网络。
- 动作数值有限但行为偏：优先查 normalization、关节顺序和 action 语义。

## 14. 针对“抓住但不会放置”的专项排查

这是当前项目最有代表性的行为问题，建议按照以下顺序，不要直接重新训练。

### 步骤一：回放原始 HDF5

```bash
conda activate isaac
cd /home/a/lwh_code/lwh_robot_learning
python3 scripts/replay_hdf5.py \
  --task Lwh-SO101-Table-v0 \
  --dataset_file datasets/hdf5/lwh_so101_table_test1_21episodes.hdf5 \
  --episode 0 \
  --camera_mode triple \
  --viewer_layout tri \
  --autoplay
```

观察：

- 原始 action 是否本身完成抓取和放置。
- 物体是否真的进入托盘。
- 末端和夹爪是否在放置后松开。
- front、wrist、overview 三个视角是否都能解释任务。

如果原始回放都不会放，模型不是主要问题，先修示教数据或仿真物理。

### 步骤二：检查成功标签是否可信

`success=True` 目前主要来自按 `N`。应将成功定义为可测量条件，例如：

```text
物体中心位于托盘内部范围
物体高度稳定在托盘底部附近
夹爪已经松开
物体在若干帧内没有弹出或滑出
```

当前任务没有完整的自动 success termination，因此操作者按错键也可能产生“成功标签”。

### 步骤三：检查数据有没有后半段

按 episode 最后 20% 帧检查：

- action 是否仍有运动。
- gripper 是否完成释放。
- object root pose 是否进入盒子范围。
- timestamp 是否在最后阶段突然中断。

很多“会抓不会放”其实是示教数据中放置阶段只占很少帧，或者 episode 在抓住后就结束了。

### 步骤四：检查时间压缩

当前样本的 HDF5 实际测得平均约 17.2 Hz，但 LeRobot 数据集 metadata 写为 30 FPS，转换器又按 30 FPS 生成均匀 timestamp。这相当于把一条约 10 秒的真实轨迹，在数据标签上压缩成约 5.7 秒左右。

这会优先伤害长时序阶段：

```text
抓取局部动作       可能仍然看起来正常
抬升、横移、对准、放置、松爪   更容易速度过快或时序不完整
```

建议实验：

1. 重新录制时先保证 measured FPS 接近 30。
2. 录制结束后检查 timestamp，不只看 metadata。
3. 临时用同一数据按实测频率做对照转换，比较闭环结果。
4. 若采用时间感知重采样，要同步处理 state、action 和两路图像。

### 步骤五：检查 state-action 一步偏移

当前 recorder 在 step 后保存 observation，再保存同一个 action。对于放置和松爪这种接触敏感动作，可能导致：

```text
模型看到“已经发生了一点动作后的状态”，却要预测造成这次变化的 action
```

重新录制或修改转换前，应先明确采用“动作前 state -> 当前 action”的监督定义。

### 步骤六：检查推理 chunk 和动作后处理

ACT checkpoint 内部 `chunk_size=100`，远程 client 的 `actions_per_chunk` 是运行时请求的动作块长度，二者是相关但不同的配置。还要检查：

- `policy_hz` 是否和数据采样频率一致。
- `max_action_delta` 是否限制过强，导致放置阶段动作跟不上。
- action queue 是否发生 underflow。
- overlapping chunk 的 `weighted_average` 是否把后半段动作过度平滑。
- 重新 reset 后是否仍混入旧 chunk。

### 步骤七：检查 checkpoint 选择

逐个比较 5k 到 30k，而不是只试最后一个。小数据集上后期 checkpoint 可能记住训练轨迹的局部模式，反而失去闭环稳定性。

## 15. 四层评估方法

### 15.1 第一层：数据结构评估

检查：

```text
HDF5 groups/attrs/datasets 完整
每个 episode 长度一致
相机存在且尺寸正确
timestamp 单调
state/action 没有 NaN/Inf
```

这是“文件能不能用”。

### 15.2 第二层：原始轨迹回放

使用 [`scripts/replay_hdf5.py`](../scripts/replay_hdf5.py)：

```bash
python3 scripts/replay_hdf5.py \
  --task Lwh-SO101-Table-v0 \
  --dataset_file datasets/hdf5/so101_table_raw.hdf5 \
  --episode 0 \
  --camera_mode triple \
  --viewer_layout tri
```

按键：

```text
B / Space       播放或暂停
N / Right       下一个 episode
P / Left        上一个 episode
R               重载当前 episode
S               暂停时单步
Q / Esc         退出
```

这是“记录下来的行为能不能在相同场景重现”。

### 15.3 第三层：固定 observation 的离线策略预测

选择固定的 HDF5 或 LeRobot 帧：

```text
给定 state + front + wrist
调用 policy
比较预测 action 与 ground-truth action
```

需要按关节维度记录：

- MAE。
- 最大误差。
- gripper 误差。
- 前半段和后半段的误差。
- 放置阶段的误差。

如果离线误差很大，问题在模型、数据或 preprocessing；如果离线误差小但闭环差，问题更可能在时间、执行、场景或反馈分布。

### 15.4 第四层：闭环仿真评估

定义成功判据，不要只凭肉眼：

```text
物体进入托盘 XY 内部范围
物体 Z 高度稳定
保持若干帧
夹爪释放
机器人没有严重碰撞或出界
```

至少跑多个初始随机种子，记录：

```text
success_rate
抓取成功率
放置成功率
平均完成时间
碰撞次数
最大动作跳变
queue underflow
```

闭环成功率才是“策略有没有完成任务”的核心指标。

## 16. 异步远程推理

### 16.1 为什么不是一帧一推理

同步方式：

```text
采集一帧 -> 上传 -> 等推理 -> 收到一个 action -> env.step
```

网络一慢，仿真和控制都被阻塞。

异步方式：

```text
主线程：60 Hz env.step(last_action)
后台发送线程：上传最新 observation
后台接收线程：接收 action chunk 放入 queue
主线程：30 Hz 从 queue 取一个 action
```

一次观测触发的是一段动作预测，所以理论上不需要每个 30 Hz action 都上传一张图。当前项目还会丢弃旧的待上传观测，只保留最新一帧，避免网络积压。

### 16.2 当前协议中的 observation

客户端发送给服务端的语义是：

```text
shoulder_pan.pos  float
shoulder_lift.pos float
elbow_flex.pos   float
wrist_flex.pos   float
wrist_roll.pos   float
gripper.pos       float
front             uint8 RGB HWC
wrist             uint8 RGB HWC
task              string
timestamp         float
timestep          int
must_go           bool
```

overview 不发送。它只是本地 GUI 的人工观察视角。

### 16.3 当前 action chunk

服务端返回一组带时间信息的动作：

```text
timestamp
timestep
action: float32[6]
```

客户端按 timestep 去重和聚合重叠 chunk，默认使用：

```text
weighted_average: old * 0.3 + new * 0.7
```

这样可以减少 chunk 交界处的跳变，但会引入平滑延迟。若任务需要快速夹爪动作，应单独评估 gripper 是否适合与机械臂关节使用相同的融合规则。

### 16.4 当前运行参数

| 参数 | 当前默认 | 技术含义 |
| --- | ---: | --- |
| 仿真控制频率 | 60 Hz | `env.step()` 目标频率 |
| `policy_hz` | 30 Hz | action queue 消费频率 |
| `render_interval` | 2 | 60 Hz physics 下约 30 Hz render/camera update |
| `actions_per_chunk` | 60 | 一次请求的运行时动作块大小 |
| `chunk_size_threshold` | 0.65 | 队列低于初始块 65% 时预取 |
| `timeout_s` | 5 s | gRPC 请求超时和重试判断 |
| `max_action_delta` | 0.05 rad | 单次新动作的限幅 |

启动本机自动管理 SSH 隧道的正式方式：

```bash
conda activate isaac
cd /home/a/lwh_code/lwh_robot_learning
python3 scripts/run_policy_client.py
```

启动脚本会读取 Python 配置：

```text
configs/remote_policy_server_config.py
```

服务器和本机的完整流程记录见 [`待阅读/服务器+本地+异步推理.md`](./服务器+本地+异步推理.md)。

### 16.5 当前远程测试结果

已经记录的 GUI 双相机测试结果：

| 指标 | 结果 |
| --- | ---: |
| IsaacLab wall loop | 约 59.2 Hz 的一轮测试；另一轮桌面环境约 40-45 Hz |
| action chunk | 15 个/600 physics steps |
| queue underflow | 0 |
| 观测上传平均延迟 | 约 449.6 ms |
| chunk 端到端平均延迟 | 约 476.2 ms |
| 服务器 ACT 推理平均耗时 | 约 12.0 ms |
| 服务器完整 chunk 平均耗时 | 约 20.8 ms |
| 小消息 gRPC RTT 中位数 | 约 36.1 ms |

结论是网络图像传输明显比 4090 推理耗时更长，所以异步队列是必要的。评估异步是否正常时，优先看 underflow 和动作连续性，而不是要求每个网络请求都在单个控制周期内返回。

### 16.6 远程链路的安全边界

当前协议使用 pickle，只适合受信任的 SSH 隧道或本机链路。不能把服务端口直接暴露到公网。服务断开时，客户端保持最后关节目标并在连续请求失败后退出；真实机器人部署还需要：

- 边缘侧 watchdog。
- 动作范围和速度限制。
- 通信超时停机策略。
- 真实 follower 的 torque/enable 安全管理。
- 人员检测和急停。

云端适合训练、模型管理和非实时推理；真实机器人低级控制闭环应尽量在机器人附近完成。

## 17. 当前项目的真实审计结果

这一节很重要：它不是“理论要求”，而是当前仓库和样本的现状。

### 17.1 当前样本基本情况

文件：

```text
datasets/hdf5/lwh_so101_table_test1_21episodes.hdf5
```

审计结果：

| 项目 | 结果 |
| --- | ---: |
| episode | 21 |
| 总帧数 | 3728 HDF5 原始帧 |
| 转换后总帧数 | 3623，跳过每段 5 帧 |
| 操作设备 | `so101leader` |
| action/state | 6D |
| 相机 | front + wrist |
| 图像 | `480x640x3` uint8 |
| metadata fps | 30 |
| episode success | 21 个都标记为 success |
| 当前物体最终中心 | 21 个样本均在简单 XY 中心范围内，但这不等于稳定放置成功 |

### 17.2 当前样本的真实 timestamp 频率

按 HDF5 timestamp 计算：

```text
总帧数：3728
各 episode 实际测得约 16.8-17.4 Hz
加权平均约 17.18 Hz
timestamp 中位间隔约 0.0561 s
```

这和 metadata 的 30 FPS 不一致。由于当前转换器不传原始 timestamp，生成的 LeRobot 数据集会以 30 FPS 重新标注帧序列。

这并不意味着现有数据一定不能做任何实验，但它意味着：

- 当前模型学习到的时间尺度不是原始墙钟时间尺度。
- `chunk_size=100` 在数据集里被解释为 3.33 秒，但原始采集的 100 个相邻样本约对应 5.8 秒。
- 远程 `policy_hz=30` 会按压缩后的时间尺度执行。
- 长动作链的后半段更容易受影响。

这是当前项目在继续追求高质量策略前最应该优先修正的实验变量。

### 17.3 当前样本的 action/state 差异

当前样本的 `action` 与 `observation/state` 平均绝对差异约为 `0.04-0.06` 弧度量级，具体关节不同。这说明 action 不是简单复制 state，而是包含位置目标和当前状态之间的控制误差；同时也说明 state/action 的时序语义必须被明确记录。

## 18. 面试官追问清单

### 18.1 环境和 IsaacLab

**问：为什么使用 Manager-Based Environment？**

答：场景、动作、观测、事件、终止条件可以通过配置类组合，通用入口只按 task id 创建环境；新任务主要新增配置和注册，不需要修改环境基类。

**问：`gym.register()` 注册的是什么？**

答：注册 task id、entry point 和环境配置入口。`Lwh-SO101-Table-v0` 最终由 IsaacLab 的 ManagerBasedRLEnv 实例化，并加载项目自定义 `LwhSO101TableEnvCfg`。

**问：为什么要把 overview 放进场景但不放进 policy？**

答：overview 方便人验证物体状态和整体轨迹，但训练输入必须稳定、明确、与 checkpoint 一致。把它混入训练会改变 feature schema，增加显存和推理带宽，也会造成训练/推理不一致。

### 18.2 数据和动作

**问：键盘和 Leader 数据能混合训练吗？**

答：当前不能直接混合。键盘是 8D IK 语义，Leader 是 6D joint position 语义。除非建立严格的动作转换并验证转换后的控制效果，否则应分开数据集。

**问：为什么每帧要保存 timestamp？**

答：用来检查真实采集节奏、跨模态同步、长尾卡顿和后续时间感知重采样。`fps` 是目标/元数据，timestamp 才反映本次实际采集。

**问：为什么不能随机删除几帧清洗？**

答：ACT 学习连续时序。随机删除会改变 action 和 image 的时间对应关系，制造人为跳跃；应优先删除整段失败 episode，或只裁连续的明确无效前后缀。

**问：HDF5 中的 env_state 为什么不训练？**

答：它包含仿真真值，例如物体 root pose，真实相机或真实机器人上未必可直接获得。它适合回放和质量分析，不应偷偷作为策略输入，否则仿真训练结果无法公平迁移。

### 18.3 训练和评估

**问：ACT loss 具体是什么？**

答：当前 LeRobot ACT 在有效 action mask 上计算 L1，开启 VAE 时再加 `kl_weight * kld_loss`。当前总 loss 是 `l1_loss + 10*kld_loss`，所以总 loss 不是纯动作 MAE。

**问：如何判断过拟合？**

答：训练 loss 继续下降，但固定样本之外的初始状态成功率下降；后期 checkpoint 离线误差可能更低，闭环稳定性却变差。需要 episode 级验证或独立 seeds，不能只看训练曲线。

**问：为什么训练集没有 validation 就有问题？**

答：当前 dataset `splits` 是 `train: 0:21`，没有独立验证集。训练 loss 只能说明模型记住训练分布，无法估计新物体位置、新初始姿态或未见轨迹的泛化能力。

**问：如果抓取成功但放置失败，先改什么？**

答：先回放原始轨迹，确认示教真的完成放置；再检查后半段是否存在、托盘是否在图像里、success 标签是否可信、时间戳是否被错误压缩、state/action 是否有一步偏移，最后才调整 chunk、限幅或重新训练。

### 18.4 异步推理和部署

**问：为什么客户端需要 action queue？**

答：网络请求和模型推理是高延迟操作，不能阻塞仿真主循环。服务端返回一段未来动作，客户端按策略频率消费；后台线程负责请求下一段，队列用来吸收网络抖动。

**问：`actions_per_chunk=60` 和 ACT `chunk_size=100` 是同一个参数吗？**

答：不是。ACT `chunk_size` 是训练/模型内部预测时域，client 的 `actions_per_chunk` 是运行时协议请求的动作块大小。二者必须通过服务端实现和测试对齐，不能只看名字相同就认为等价。

**问：GPU 60% 是否说明还有 40% 性能可以直接拿来提高控制频率？**

答：不一定。瓶颈可能在渲染同步、CPU 数据拷贝、网络、线程等待、单流推理或物理 step。要看端到端 profile 和 queue underflow，不能用总 GPU 利用率单独下结论。

**问：这个远程架构能直接用于真实机器人吗？**

答：当前适合仿真验证。真实部署不能把跨公网的 server 作为唯一低级控制回路，应把相机、推理、动作限幅、watchdog 和急停放在边缘端；云端可用于训练、模型管理和非实时任务。FlashRT 等推理加速器应在保留原生回退路径的前提下，比较动作一致性和 P50/P95/P99 延迟后再接入。
